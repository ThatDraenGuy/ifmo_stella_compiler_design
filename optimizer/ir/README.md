# Stella IR для оптимизатора

Этот справочник описывает данные, с которыми работает ваша программа на этапе 2. Обязательные преобразования, критерии и примеры даны в [задании](../../stage-2.pdf). Входы заранее проверены командой `./stella ir-check`; свой верификатор и интерпретатор писать не требуется.

Выберите JSON или SIR. У них одна структура: [JSON Schema](unit.schema.json) задаёт поля записей, [грамматики](../grammar/README.md) — текстовый синтаксис. Схема не проверяет типы, доминирование или лексическую область видимости; для этого используйте предоставленный верификатор.

## Модуль, имена и значения

JSON-модуль содержит все следующие поля:

```json
{
  "format": "stella-ir", "version": "1",
  "profile": "stella-ir-base-v1", "form": "cfg",
  "exports": [], "layouts": [], "frames": [], "callables": []
}
```

`form` принимает значения `cfg`, `ssa`, `functional`. Сохраняйте `format`, `version`, `profile`, экспортируемые имена, описания объектов и кадров, имена и сигнатуры вызываемых сущностей. Профиль выбирает операции среды времени выполнения. Для обязательных проходов их внутреннее устройство не требуется: правила сохранения перечислены ниже.

Имена соответствуют `[A-Za-z_][A-Za-z0-9_]*` и чувствительны к регистру. У вызываемых сущностей, описаний объектов и описаний кадров отдельные пространства имён. Имена значений и блоков локальны внутри тела. Ссылки на объявления могут предшествовать объявлениям. `exports` перечисляет обычные функции, доступные снаружи, в том числе функции без вызовов внутри модуля. Особого имени `main` в IR нет.

Типов ровно три: `i64`, `bool`, `ref`. `ref` обозначает управляемый объект, а не числовой адрес. Неявных преобразований типов и литерала ссылки нет.

| Запись JSON | Назначение | Запись в SIR |
|---|---|---|
| `{"name":"x","type":"i64"}` | Имя с типом (binding) | `%x: i64` |
| `{"var":"x"}` | Операнд: значение переменной | `%x` |
| `{"i64":"123"}` | Операнд: целая константа | `123` |
| `{"bool":true}` | Операнд: булева константа | `true` |

Константы разрешены во всех позициях операндов, в том числе в φ-функциях. Числа в JSON записываются десятичными строками. Для `i64` допустимы `0` или `-?[1-9][0-9]*` в диапазоне от −9223372036854775808 до 9223372036854775807. Знак `+`, ведущие нули и `-0` недопустимы. Литерал вне диапазона не оборачивается.

## Вызываемые сущности и графы

Обычная функция содержит `kind: "function"`, `name`, `params` (список bindings), `result` (тип) и поля тела. Процедура содержит `kind: "routine"`, `name`, `params` и поля тела; поля `result` у неё нет. Обычная функция возвращает значение. Процедура передаёт управление явно. Обрабатывайте тела обоих видов одинаковыми внутрипроцедурными анализами.

| Форма | Поля тела | Определения значений |
|---|---|---|
| CFG | `locals`, `entry`, `blocks` | `locals` — список bindings, не включая параметры. Параметры и переменные можно присваивать повторно. Результат инструкции использует уже объявленное имя и тот же тип. |
| SSA | `entry`, `blocks` | Параметр, результат инструкции или φ определяет имя ровно один раз во всём теле. `locals` отсутствует. |
| Functional | `body` | Выражения с неизменяемыми bindings и локальными функциями, описанные ниже. Поля графа отсутствуют. |

Блок содержит `name`, `instructions` и `terminator`. `entry` именует существующий блок без предшественников. Переходы явные: порядка блоков в массиве недостаточно для перехода. Рёбра графа создают только `jump` и `branch`. Вызов функции и передача управления процедуре не создают внутрипроцедурных рёбер.

Недостижимые блоки разрешены. Имена и типы в них остаются корректными. Определённость переменных CFG и доминирование SSA проверяются только на достижимых путях. В CFG перед каждым использованием переменная должна быть определена на всех достижимых путях до него; при входе определены только параметры.

В SSA определение доминирует каждое обычное использование и предшествует ему внутри блока. Использование в φ относится к концу соответствующего предшественника. Определение такого операнда не обязано доминировать блок с φ.

## Инструкции и арифметика

Обычная инструкция содержит `op`, `args` (список операндов) и `results` (список bindings). Все аргументы читаются до присваивания результатов. Имена результатов одной инструкции различны. Например:

```json
{"op":"add","args":[{"var":"x"},{"i64":"1"}],
 "results":[{"name":"next","type":"i64"}]}
```

```text
[%next: i64] = add(%x, 1);
```

| `op` | Типы аргументов | Тип единственного результата | Значение |
|---|---|---|---|
| `copy` | `T` | `T` | То же значение, в том числе ссылка |
| `add`, `sub`, `mul` | `i64`, `i64` | `i64` | Арифметика по модулю 2⁶⁴ |
| `div`, `rem` | `i64`, `i64` | `i64` | Знаковые частное и остаток |
| `eq`, `ne` | Два `i64` или два `bool` | `bool` | Равенство или неравенство |
| `lt`, `le`, `gt`, `ge` | `i64`, `i64` | `bool` | Знаковое сравнение |
| `not` | `bool` | `bool` | Отрицание |
| `and`, `or`, `xor` | `bool`, `bool` | `bool` | Булевы операции над уже вычисленными аргументами |

Деление округляется к нулю. Ненулевой остаток имеет знак делимого. Для минимального `i64` и делителя `-1` частное равно минимальному `i64`, остаток равен нулю. Деление и остаток при нулевом делителе завершают исполнение ошибкой `arithmetic-zero`. Остальные скалярные операции не имеют эффектов и не завершаются ошибкой. Сравнения ссылок нет.

У следующих инструкций есть дополнительные поля:

| `op` | Дополнительные поля | Правило для оптимизатора |
|---|---|---|
| `call` | `callee`: имя обычной функции | Сохранить вызов, все аргументы и один результат; вызов может иметь эффекты, завершиться ошибкой или не завершиться. |
| `run` | `target`: имя процедуры | Те же консервативные правила; одна возвращаемая величина приходит из исполнения процедуры. |
| `runtime` | `name`: строка; `attributes`: JSON-объект | Сохранить операцию, атрибуты, порядок и все позиции аргументов и результатов. Результатов может быть ноль, один или несколько. |

В обязательных анализах результаты этих трёх видов неизвестны. Они не кандидаты для CSE или удаления как неиспользуемые вычисления. Недостижимый блок с ними можно удалить. Замена их операндов эквивалентными значениями и согласованное переименование допустимы.

Все использования локальных значений явны в `args`, все определения — в `results`. Значениями полей `attributes` бывают строки, булевы значения, массивы и объекты таких значений. Числа записываются строками; `null` не допускается. Атрибуты не содержат скрытых локальных операндов или тел кода. Не считайте строку в атрибуте именем переменной и не переименовывайте её.

Например, событие наблюдения использует `%x`, хотя результата нет:

```text
[] = runtime "trace.emit"(%x) {"label":"answer"};
```

Операции с кучей и кадрами обрабатываются по тем же правилам. Реализовывать их исполнение для этапа 2 не нужно.

## φ-функции и завершения блоков

В начале SSA-блока может быть любое число φ-функций. Они предшествуют обычным инструкциям и имеют ровно один результат:

```json
{"op":"phi","results":[{"name":"x","type":"i64"}],
 "incoming":[{"pred":"left","value":{"i64":"1"}},
             {"pred":"right","value":{"var":"y"}}]}
```

```text
%x: i64 = phi {^left: 1, ^right: %y};
```

У φ нет `args`. `incoming` содержит ровно одну альтернативу для каждого синтаксического предшественника, включая недостижимые; предшественников может быть больше двух. Все φ выбирают операнды по одному предшественнику и присваивают результаты одновременно. При изменении рёбер обновляйте `incoming`. В недостижимом блоке без предшественников разрешена φ без альтернатив. Во входном блоке φ нет.

Каждый графовый блок имеет ровно одно завершение:

| `op` | Остальные поля JSON | Использования и переход |
|---|---|---|
| `jump` | `target` | Переход к блоку своего тела |
| `branch` | `args`, `then`, `else` | Один операнд `bool`; два различных блока |
| `return` | `args` | Один операнд типа результата обычной функции |
| `tail` | `target`, `args` | Передача всех аргументов именованной процедуре |
| `tail-entry` | `signature`, `args` | Первый аргумент — объект `ref`, остальные соответствуют списку типов `signature` |
| `resume` | `args` | Один операнд, передаваемый продолжению |
| `fail` | `error` | Завершение с указанным кодом ошибки; операндов нет |

`return` разрешён только в функции, `tail`, `tail-entry`, `resume` — только в процедуре. У последних трёх нет локального блока-преемника. Сохраняйте каждый их операнд при переименовании и анализе зависимостей. `error` — строка вида `[a-z][a-z0-9-]*`; разные коды обозначают разные исходы. Ошибка завершает исполнение целиком.

## Функциональный выход

Этот раздел нужен при выборе выхода Functional. Выражение различается по `op`:

| `op` | Остальные поля JSON | Значение |
|---|---|---|
| `let` | `instruction`, `body` | Выполнить инструкцию с непустым `results`, связать результаты в `body` |
| `do` | `instruction`, `body` | Выполнить инструкцию без результатов и продолжить |
| `if` | `condition`, `then`, `else` | По операнду `bool` выбрать одно из двух выражений |
| `letrec` | `functions`, `body` | Связать непустую группу локальных функций и выполнить `body` |
| `jump` | `target`, `args` | Хвостовой переход к локальной функции с передачей аргументов |
| `return`, `tail`, `tail-entry`, `resume`, `fail` | Как в таблице завершений | Завершение с тем же смыслом |

Локальная функция имеет только `name`, `params` и `body`. Это функция потока управления: `return` в ней возвращает результат из внешней обычной функции. Она не является значением или замыканием в куче. Переход к ней не накапливает стек возвратов.

Имена функций группы `letrec` видны друг другу и в следующем `body`. Тело функции видит внешние значения и собственные параметры, но не параметры соседней функции или значения, связанные позже. Результаты `let` не видны в аргументах его инструкции. Имена всех значений уникальны во всём внешнем теле; имена локальных функций тоже уникальны в своём пространстве. Уникальность не заменяет лексическую область видимости.

При выходе из SSA можно передавать значения параметрами или захватывать их из допустимой внешней области. Локальная функция не обязана соответствовать ровно одному исходному блоку. В этой форме нет φ и графовых `branch`.

## Объявления, которые нужно сохранять

Эти записи нужны для сохранения модуля; размещение объектов и стеков в памяти не входит в задание.

| Объявление | Обязательные поля JSON |
|---|---|
| Элемент `layouts` | `name`, `fields` (список типов), `capacity` (неотрицательная десятичная строка), `entry` (`null` или имя процедуры), `updatable` (`bool`) |
| Элемент `frames` | `name`, `saved` (список типов), `result` (тип), `target` (имя процедуры) |

Имена из `entry` и `target` — ссылки на вызываемые сущности. Процедуру нельзя считать недостижимой только из-за отсутствия прямого вызова. Операнды, сохраняемые в кадре, остаются использованиями значений, даже если продолжение будет вызвано позже.

## Кодировка и проверка результата

Оба формата используют UTF-8. JSON не допускает лишних полей, повторяющихся ключей и комментариев. Порядок ключей не важен. Порядок аргументов, результатов, инструкций, параметров и полей объектов важен; порядок объявлений, блоков и альтернатив φ не выбирает путь исполнения.

Заголовок SIR — `stella-ir 1 FORM "PROFILE";`. Сигил и имя составляют один токен: `%x` — значение, `@f` — вызываемая сущность, `$L` — описание объекта, `!K` — описание кадра, `^b` — блок или локальная функция. Внутри токена нет пробела. Строки и объекты атрибутов используют JSON-экранирование; `//` начинает комментарий до конца строки вне строки JSON и объекта атрибутов. В CFG строка `locals (...);` обязательна, даже при пустом списке; в SSA она отсутствует. Все списки результатов заключены в `[...]`, кроме отдельного синтаксиса φ.

Проверяйте результат через `./stella ir-check`. Для проверки поведения используйте `ir-run-source` с файлом интерфейса исходной Stella или `ir-run` для прямого IR-примера. Преобразование должно сохранять результат, наблюдаемые изменения и совместное использование объектов кучи, порядок событий, код ошибки и незавершение. Потребление памяти, число шагов и момент исчерпания ресурса могут измениться. Успех верификатора сам по себе не доказывает сохранение поведения.

## Источники

Справочник — сокращённое изложение контракта Stella IR v1 для этого задания. Он не добавляет новых правил IR. SSA и функциональная форма следуют главе 19 книги Эндрю Аппеля «Modern Compiler Implementation in ML»; библиография приведена в задании. Имена записей, текстовый формат и примеры кодировки определены в Stella. Схема использует JSON Schema Draft 2020-12. Грамматики и примеры чтения/печати также предоставлены проектом Stella; это готовые компоненты для ввода и вывода, а алгоритмы преобразований вы реализуете самостоятельно.

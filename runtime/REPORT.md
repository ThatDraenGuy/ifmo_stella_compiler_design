## Сборка и запуск

Реализовано на C, с небольшой опорой на заглушку (оттуда были украдены валидации аргументов abi-функций и align выделяемых объектов)

Зависимости:
- cmake (3.27+)
- clang или gcc
- docker

Проверялось на Linux с использованием clang 22.1.8/gcc 16.2.1/docker 29.8.2 (gcc на моей системе не собирает Debug-конфигурацию, но спокойно справляется с стандартной конфигурацией).

Для сборки и запуска конкретной stella-программы предоставлен утилитный скрипт. Рекомендуется:
1) Перейти в директорию runtime
2) Из этой директории запустить скрипт run-program.sh, передав ему первым аргументом путь до stella-файла (абсолютный или относительно директории runtime), а последующими аргументами - аргументы для запуска stella-программы (входной аргумент и макс. размер кучи)

Этот скрипт сконфигурирует cmake-сборку с целевым stella-файлом,прогонит саму сборку, и запустит собранную программу. Выставленные перед скриптом env-переменные дойдут до пользовательской программы. Например:
```sh
$ STELLA_GC_STATS=1 STELLA_GC_COLLECT_START_THRESHOLD=0.8 ./run-program.sh test/stella/src/garbage.stella 30 4096
unit
GC stats
requested bytes: 13920
...
```

"Под капотом" подключение пользовательской программы реализуется через выставление в конфигурации cmake переменной USER_SRC_ST (stella-исходник) или USER_SRC_С (c-исходник). Для stella-исходника cmake сам вызовет docker-контейнер с транслятором стеллы в C. получившийся пользовательский исходник включается в цель исполняемого файла `stellac_runtime_app`.

Для сборки и запуска тестов предоставлен утилитный скрипт. Рекомендуется:
1) Перейти в директорию runtime
2) Запустить скрипт run-tests.sh


## Алгоритм и устройство реализации

Реализован алгоритм Бейкера (Чени + инкрементальная сборка).

При инициализации сборщика выделяется два полупространства, оба размерами max_heap_bytes.
- где-то в середине разработки я хотел сделать динамический размер кучи, расширяющийся и сужающийся по мере её заполнения/"успевания" проведения сборки, но по итогу от этой идеи я отказался. В основном из-за поля `fields` в `StellaObject`, из-за которого делать ре-аллокацию пространств кучи было по сути невозможно (потому что пришлось бы обновлять это поле для каждого объекта индивидуально, хотя по сути, никакой необходимости в этом поле нет, и структура `StellaObject` могла бы спокойно существовать без него или с free-array членом на конце. Но раз уж прописано в условии что нужно заполнять, приходится заполнять)

Если при очередной аллокации (в from-space) обнаруживается, что куча будет занята свыше порога, то начинается процесс сборки. Переносятся корни, а аллоцирующийся объект сразу помещается в конец to-space. Перед каждой последующей аллокацией проводится установленное число шагов сборки.

Если при очередной аллокации (в конец to-space) обнаруживается, что куча будет занята свыше порога, то начинается сканирование вне-бюджета (сборщик пытается завершить текущую сборку). После завершения сборки будет произведена попытка поместить аллоцирующийся объект в from-space по алгоритму выше (который всегда вызовет начало новой сборки из-за "заполненности" кучи).

При завершении сборки происходит смена указателей на to- и from-space, перевыделение памяти не происходит.

Если во время сканирования вне-бюджета заканчивается место в куче, сборщик останавливает работу с OOM (попыток очистить "свежий" мусор не производится).

По сути весь алгоритм находится в исходном файле [heap.c](./src/heap.c).

## Параметры
Все параметры перечислены в структуре [GcConfig](./include/internal/config.h).
- max_heap_bytes - "стандартный" параметр, передаётся в stella_gc_init. Определяет размер каждого полупространства кучи в байтах
- collect_steps_count - число шагов сборки, выполняющихся на один запрос аллокации. Передаётся через env-переменную STELLA_GC_COLLECT_STEPS_COUNT (натуральное число). Значение по умолчанию - 3
- collect_start_threshold - доля кучи, являющаяся порогом начала/конца сборки. Передаётся через env-переменную STELLA_GC_COLLECT_START_THRESHOLD (double, >0, <=1.0). Значение по умолчанию - 0.8
- json_stats - флаг json-формата вывода статистики. Если установлен в 1, то статистика будет выведена в json-формате (используется в тестах). Значение по умолчанию - 0

## Статистика и состояние
Все единицы статистики перечислены в структуре [GcStats](./include/internal/stats.h)
- requested bytes: число запрошенных для аллокации байтов
- rounded bytes: число запрошенных для аллокации байтов с учётом align-занимаемых байтов
- allocs: число запрошенных аллокаций
- collections: число начатых процессов сборки
- collection_steps: число проделанных шагов сборки
- occupied_bytes: число занятых в куче байтов в момент вывода статистики
maximum_occupied_bytes: максимальное число занятых в куче байтов за время выполнения программы
- managed_reads: число вызовов stella_gc_read_managed
- managed_writes: число вызовов stella_gc_write_managed (+ число записей в managed-поля в stella_gc_update_object)
- primitive_reads: число вызовов stella_gc_read_primitive
- primitive_writes: число вызовов stella_gc_write_primitive (+ число записей в primitive-поля в stella_gc_update_object)
- read_barrier_activations: число активаций read-барьера. "Активацией" считается вызов forward в функции stella_gc_read_managed, изменивший указатель на читаемое поле (т.е. считаются как forward, реально переносящие объект между пространствами, так и forward, возвращающий ссылку уже перенесённого объекта из его `gc_word`).
- dynamic_root_depth: глубина стека динамических корней в момент вывода статистики
- maximum_dynamic_root_depth: максимальная глубина стека динамических корней за время выполнения программы
- permanent_root_count: глубина стека постоянных корней в момент вывода статистики
- out_of_budget_scans: число сканирований вне-бюджета
- heap_size: размер кучи (размер в байтах одного полупространства, всегда равно max_heap_bytes)

Пример вывода статистики:
```sh
$ STELLA_GC_STATS_JSON=1 STELLA_GC_STATS=1 STELLA_GC_COLLECT_START_THRESHOLD=0.8 ./run-program.sh test/stella/src/garbage.stella 30 4096
unit
```
